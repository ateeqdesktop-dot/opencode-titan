ملخص تنفيذي
TITAN هو نظام تنسيق وكلاء برمجيين يعمل أصليًا داخل OpenCode V2. لا يهدف إلى تكثير الوكلاء، بل إلى تحويل طلب تطوير برمجي إلى دورة عمل قابلة للتتبع: فهم المتطلبات، استكشاف المستودع، بناء خطة واعتمادها، تقسيم العمل إلى رسم مهام DAG، تعيين وكلاء وجلسات OpenCode، تشغيل المهام بالتوازي ضمن حدود آمنة، دمج التغييرات، التحقق المستقل، إصلاح الفشل، ثم تسليم نتيجة مدعومة بأدلة.
القرار المعماري الأساسي هو أن OpenCode يظل محرك تشغيل النماذج والجلسات والأدوات والصلاحيات، بينما يملك TITAN منطق التنسيق وحالة سير العمل وسجل المهام والتحقق والميزانية. يجب ألا يعيد TITAN تنفيذ ما يوفره OpenCode بالفعل، وألا يعتمد على واجهات V1 القديمة. واجهة الإضافة المستهدفة هي ⁦@opencode/plugin⁩ مع ⁦Plugin.define⁩ و⁦setup(ctx)⁩، مع جزء TUI اختياري عبر ⁦⁦@opencode/plugin⁩/tui⁩. [S1][S2]
الوثيقة تفصل بين المتطلبات الإلزامية للنسخة الأولى وبين القدرات المتقدمة التي تُسلّم تدريجيًا. كما تحدد حدود الاستقلالية: المهام منخفضة المخاطر يمكن أن تعمل تلقائيًا ضمن سياسات المشروع، أما الحذف والنشر والدفع إلى الفروع المحمية وتغيير الاعتماديات الحساسة والوصول إلى الأسرار فتتطلب موافقة صريحة.

1. المقدمة والغرض والنطاق
1.1 الغرض
تحدد هذه الوثيقة المتطلبات الوظيفية وغير الوظيفية لنظام TITAN، بما في ذلك واجهات المستخدم، والتكامل مع OpenCode V2، ونموذج الوكلاء، ومحرك التخطيط والجدولة، والعزل، والتحقق، والتعافي، والذاكرة، والأمن، والتشغيل. وهي موجّهة لتكون أساسًا قابلًا للتنفيذ والتقييم، لا وصفًا تسويقيًا.
1.2 نطاق المنتج
•  إضافة OpenCode V2 محلية-أولًا، تتكون مبدئيًا من مكوّن Server Plugin ومكوّن TUI Plugin اختياري، مع عقد RPC typed عند الحاجة للتواصل بينهما. يدعم OpenCode حزمًا تتضمن أجزاء server وTUI وRPC؛ جزء GUI تجريبي ويُستبعد من النطاق الأول. [S1][S3]
•  إدارة طلبات التطوير من مهمة صغيرة إلى ميزة متعددة الملفات أو مشروع متعدد المكونات، مع توجيه مباشر للمهام البسيطة وتنسيق أثقل للمهام المعقدة فقط.
•  تعريف أدوار الوكلاء وملفات قدراتهم وسياساتهم ونماذجهم المسموح بها، ثم إنشاء جلسات OpenCode مستقلة لكل عامل أو مهمة عند الحاجة.
•  إدارة خطة ومهام مترابطة (DAG)، ورسائل وتسليمات وأدلة تنفيذ، وحالة دائمة قابلة للاستعادة بعد إعادة تشغيل OpenCode.
•  تشغيل مهام قراءة متوازية، ومهام كتابة معزولة عند الحاجة عبر Git Worktrees، ثم مراجعة ودمج مضبوطين.
•  اختبارات وجودة وأمن وتقرير ختامي يربط كل معيار قبول بدليل قابل للفحص.
•  العمل محليًا داخل مشروع المستخدم، مع التكامل الاختياري مع مزودي النماذج وMCP والبحث والوثائق عبر قدرات OpenCode المهيأة من المستخدم.
1.3 ما هو خارج النطاق (الإصدار الأول)
•  تدريب أو ضبط أوزان نماذج الذكاء الاصطناعي، أو استضافة نماذج خاصة.
•  خدمة SaaS أو لوحة تحكم سحابية متعددة المستأجرين أو مزامنة فرق عن بعد.
•  دمج تلقائي إلى الفرع الافتراضي، أو نشر إنتاجي، أو إصدار حزم، أو نشر أسرار دون موافقة بشرية منفصلة.
•  ضمان صحة الكود أو منع جميع الهجمات أو الاستغناء عن المراجعة البشرية في التغييرات عالية الخطورة.
•  إعادة كتابة نظام إدارة الجلسات أو مزودي النماذج أو صلاحيات OpenCode؛ هذه تبقى مسؤولية OpenCode.

2. الرؤية والأهداف ومقاييس النجاح
2.1 بيان الرؤية
الرؤية — تحويل OpenCode V2 من جلسة مساعد واحدة إلى فريق هندسي قابل للإدارة، يعمل بخطة واضحة وحالة دائمة وصلاحيات محدودة وتحقيق مستقل، مع إبقاء الإنسان صاحب القرار النهائي في الإجراءات ذات الأثر المرتفع.

2.3 مبادئ التصميم غير القابلة للتفاوض
•  التحقق قبل الادعاء: لا يعلن النظام اكتمال المهمة اعتمادًا على كلام الوكيل وحده.
•  الأدلة قبل الثقة: قرارات الإكمال مبنية على نتائج أدوات واختبارات ومراجعة ونطاق التغيير.
•  العزل قبل التوازي الكتابي: لا يسمح النظام بوكلاء متعددين بتعديل مساحة عمل واحدة بلا سياسة واضحة.
•  الحد الأدنى من الصلاحيات: لكل وكيل أقل صلاحيات تكفي لإنجاز المهمة.
•  الاستعادة قبل السرعة: حالة العمل المؤكدة لا تضيع عند الانقطاع.
•  التوجيه المتكيف وليس الإجباري: لا يطلق فريقًا كبيرًا لمهمة صغيرة.
•  OpenCode هو المضيف: يستخدم TITAN واجهات V2 الموثقة ولا يعتمد على تفاصيل داخلية غير مستقرة.
2.4 ما لا يعد مقياس نجاح
عدد الوكلاء، وعدد الاستدعاءات، وكمية الرموز، وحجم السجلات، وعدد النجوم على GitHub ليست مقاييس جودة نهائية. لا يُقبل أي تحسين في هذه الأرقام إذا خفّض دقة التنفيذ أو زاد التكلفة أو المخاطر دون عائد واضح.

3.1 افتراضات المستخدم
•  المستخدم لديه تثبيت OpenCode V2 عاملًا، ونموذج واحد على الأقل ومزودًا مهيأً.
•  المشروع المستهدف موجود محليًا، ويُفضّل أن يكون مستودع Git.
•  المستخدم يعرف أن نتائج النماذج احتمالية، ويوافق على مراجعة التغييرات عالية الأثر.
•  المستخدم يستطيع اختيار مستوى الاستقلالية وسقف الإنفاق وحدود التوازي.
4. سياق المنتج وحدوده
4.1 سياق التشغيل
يعمل TITAN بوصفه إضافة داخل مضيف OpenCode V2. جزء الخادم يضيف أدوات/أوامر وخطافات وتكاملات وسلوك تنسيق؛ وجزء TUI يعرض أوامر وحالة تشغيل ولوحة مراقبة نصية. يمكن للحزمة أن تتضمن عقد RPC مشتركًا بين الجزءين. توثيق V2 يحدد هذه الأجزاء ومسارات تحميلها بصورة صريحة. [S1][S3]

4.4 حدود الاستقلالية
الاستقلالية ليست مفتاح تشغيل/إيقاف واحدًا؛ إنها سياسة لكل إجراء. المراجعة والاختبارات يمكن أن تعمل تلقائيًا، لكن الدفع إلى فرع بعيد أو الدمج إلى فرع محمي أو النشر أو حذف بيانات أو تعديل أسرار أو الاتصال بنطاق خارجي غير مصرح به يظل محظورًا أو يتطلب موافقة صريحة. يجب أن تتغلب سياسة الأمان على أي طلب صادر من وكيل أو ملف تعليمات داخل المستودع.

5.3 بنية الفريق
يعتمد المنتج على كتالوج أدوار قابل للتخصيص، لا على 22 وكيلًا ثابتًا يجب تشغيلهم. الدور يحدد الهدف، والمدخلات المطلوبة، والمهارات، والأدوات المسموح بها، ونوع مساحة العمل، والنموذج المفضل/البديل، ومخرجات JSON المتوقعة، وحدود التنفيذ. تُنشأ جلسات العامل عند الحاجة وتغلق/تؤرشف وفق سياسة الاحتفاظ.

5.4 قواعد تشكيل الفريق
•  المهام الصغيرة تُنفذ بوكلاء أقل؛ التوازي لا يُستخدم إلا عندما توجد مهام مستقلة واضحة.
•  العدد الافتراضي الأقصى للعمال المتزامنين هو 4، ويمكن رفعه حتى حد منتج أولي قابل للتهيئة 8 بعد قياس التكلفة والموارد. هذا حد تصميمي لـ TITAN وليس حدًا تفرضه OpenCode.
•  المهام التي تتشارك ملفًا أو عقدًا معماريًا حرجًا لا تنفذ كتابة متزامنة عليه دون قفل/تقسيم نطاق أو Worktree منفصل.
•  تمنع الوكلاء المتداخلين افتراضيًا؛ العامل لا ينشئ فريقًا آخر إلا إذا سمحت سياسة صريحة وبحد عمق معلوم.
•  يُخصص مراجع مستقل عن منفذ التغيير في المهام عالية المخاطر أو الكبيرة.
5.5 نموذج التنسيق: DAG لا محادثة حرة
يجب أن يمثل كل عمل كعقد Task محدد ومدخلات ومخرجات واعتماديات ومعايير قبول. المحادثات بين الوكلاء وسيلة للتنسيق وليست سجل الحالة. محرك DAG يحدد ما هو جاهز للتنفيذ، ويمنع بدء المهام قبل اكتمال تبعياتها، ويرفض أي دورة في الرسم البياني.

8.3 آلة حالات Task
الحالات المقترحة: DRAFT، BLOCKED، READY، QUEUED، RUNNING، WAITING_APPROVAL، VERIFYING، NEEDS_REWORK، SUCCEEDED، FAILED، CANCELLED، SKIPPED. يجب أن يحدد محرك الحالة انتقالات مسموحة، ويمنع مثلًا الانتقال من FAILED مباشرة إلى SUCCEEDED دون إعادة تشغيل أو اعتماد استثناء.
8.4 قواعد التخزين والاحتفاظ
•  يكون سجل TITAN هو مصدر الحقيقة لحالة التنسيق، بينما تظل سجلات جلسات OpenCode مصدرًا لحالة تنفيذ النموذج نفسها.
•  تُحفظ كل انتقالات الحالة المهمة في معاملة ذرية مع سجل الحدث المقابل.
•  الحد الأدنى المقترح للاحتفاظ ببيانات Run المكتملة 90 يومًا، قابل للتعديل من المستخدم. ملفات المحادثات تبقى وفق سياسة OpenCode ولا تُنسخ تلقائيًا إلى قاعدة TITAN.
•  تُخزن مراجع الملفات والـ hashes بدل نسخ محتوى كبير متى أمكن؛ ويجب أن تكون كل artifact مرتبطة بمصدرها ومهمتها.
•  يجب أن يتضمن مخطط التخزين schemaVersion وخطة ترحيل قابلة للنسخ الاحتياطي والرجوع.
8.5 استراتيجية قاعدة البيانات
التوصية الأولية قاعدة محلية معاملاتية مثل SQLite مع WAL إذا أثبت اختبار PoC توافق برنامج التشغيل مع بيئة Bun/Node الفعلية التي يستضيفها OpenCode. يُعزل الوصول خلف Persistence Adapter حتى يمكن تبديل التنفيذ دون تغيير منطق المجال. لا تُعد ⁦ctx.storage⁩ بديلًا تلقائيًا لقاعدة بيانات معاملاتية؛ تستخدم لتفضيلات/قيم صغيرة فقط ما لم تثبت خصائصها المطلوبة عبر الوثائق والاختبارات.
9. الواجهات الخارجية والتكامل مع OpenCode V2
9.1 واجهة الإضافة
المتطلب الأساسي هو إنشاء إضافة V2 ذات معرف ثابت وتسجيلها عبر ⁦Plugin.define⁩ و⁦setup(ctx)⁩. توثيق OpenCode يوضح أن الجزء Server يعمل داخل خادم OpenCode ويضيف الأدوات والخطافات والتكاملات والأوامر والوكلاء؛ وجزء TUI مستقل؛ ويمكن للحزمة مشاركة عقد RPC typed. [S1][S2]
import { Plugin } from "⁦@opencode/plugin⁩"export default ⁦Plugin.define⁩({  id: "titan.orchestrator",  async ⁦setup(ctx)⁩ {    // Register TITAN tools, hooks and integrations here.    // Return cleanup to stop workers and dispose subscriptions.    return () => { /* graceful shutdown */ }  },})
المثال هيكل توضيحي؛ أسماء العمليات الدقيقة يجب أن تُطابق إصدار ⁦@opencode/plugin⁩ المثبت وملفات الأنواع الرسمية عند التنفيذ. لا تعتمد هذه الوثيقة على أسماء API غير مؤكدة أو على واجهات داخلية.
9.2 واجهة TUI وRPC
يستخدم مكوّن TUI الحزمة ⁦⁦@opencode/plugin⁩/tui⁩ ويقدم أوامر/مسارات/تنبيهات وعرضًا محليًا. عند فصل واجهة المستخدم عن منطق الخادم، يجب أن يمر الاستدعاء عبر RPC typed ذي مخطط إصدار واضح. يجب ألا يسمح TUI بتجاوز موافقات الخادم أو الصلاحيات.
9.3 الجلسات والوكلاء الفرعيون
يوفر OpenCode V2 أوضاعًا للوكلاء primary وsubagent وall؛ والوكلاء الفرعيون يعملون في جلسات طفلة بسياق جديد، ويخضع إطلاقهم لصلاحية subagent للوكيل الأب بينما يستخدم الطفل صلاحياته الخاصة. يجب أن يستفيد TITAN من ذلك بدل محاكاة جلسات وهمية، مع الاحتفاظ بسجل فريقه ومهامه الخاص. [S4]
9.4 أحداث OpenCode
قاعدة موثوقية حاسمة — لا تجعل event stream الخاص بـ OpenCode مصدر الحقيقة الوحيد: توثيق API يصف الاشتراك بالأحداث بأنه متطاير؛ قد تفقد الأحداث أثناء الانقطاع وقد يفشل المستهلك البطيء عند تجاوز السعة. يجب حفظ انتقالات TITAN في سجله الدائم، ثم المصالحة مع حالة OpenCode بعد عودة الاتصال. [S5]
يستفيد TITAN من أحداث الجلسات والأدوات والصلاحيات وWorktree لمراقبة التنفيذ، لكنه لا يفترض أن كل حدث سيصل. يجب أن تكون كل معالجة أحداث idempotent وأن يحتوي الحدث الداخلي على sequence وcorrelationID.
9.5 Worktrees وVCS
يجب استخدام واجهات Worktree/VCS الموثقة في OpenCode V2 عبر adapter. توثق واجهة SDK عمليات إنشاء وتحديث وإزالة Worktree، وتحتاج بعض عمليات Worktree إلى projectID في واجهة SDK المضمنة. تُتحقق متطلبات المشروع والفرع والاستراتيجية الفعلية من API المثبتة، لا من نسخ أمثلة غير متوافقة. [S6]
9.6 نماذج ومزودون
يتكامل TITAN مع كتالوج النماذج والمزودين داخل OpenCode ويختار من المتاح للمستخدم. لا يخزن أسرار المصادقة ولا ينشئ اتصالًا مباشرًا بمزود ما لم تكن هذه إضافة منفصلة موثقة وموافقًا عليها. يجب عدم الاعتماد على خصائص طلب وكيل لا يرسلها مشغل V2 فعليًا؛ وثائق الوكلاء تشير إلى أن بعض overlays محفوظة لكنها لا تُرسل بعد في طلبات النموذج. لذلك يجب اعتماد الإعدادات التي يدعمها المزود/النموذج رسميًا فقط. 11. الأمن والخصوصية ونموذج التهديد
11.1 الأصول التي يجب حمايتها
•  أسرار المزودين ورموز المصادقة وملفات البيئة.
•  كود المصدر والبيانات الخاصة والملفات خارج مساحة العمل.
•  سجل الجلسات والرسائل والذاكرة والتقارير.
•  Git branches وcommits وبيانات المستخدم غير المحفوظة.
•  ميزانية الاستخدام وحسابات المزودين.
•  سلامة سياسات الأمان وموافقات المستخدم.
11.2 نموذج التهديدات
التهديد
مثال على الهجوم/الفشل
الضابط المطلوب
Prompt Injection
تعليمات خبيثة داخل README أو issue أو صفحة ويب تطلب كشف secrets أو تجاوز السياسة.
اعتبار المحتوى بيانات؛ صلاحيات أدوات خارج النموذج؛ حظر الوصول للأسرار؛ مراجعة أفعال الشبكة.
Excessive Agency
وكيل يحصل على push/deploy أو حذف ملفات بلا داعٍ.
Least privilege، موافقات مرتبطة بإجراء، deny افتراضي للأفعال الخطرة.
Sensitive Data Disclosure
تسريب محتوى .env إلى prompt أو logs أو مزود غير مسموح.
تنقيح، allowlist للمزود، منع قراءة الأسرار، فصل ذاكرة المشروع.
Supply Chain
اعتماد package أو plugin مخترق أو نسخة غير مثبتة.
lockfile، إصدار مثبت، فحص تراخيص وثغرات، قائمة مصدر موثوق.
Unbounded Consumption
حلقة agent spawning/retries أو prompt ضخم يؤدي لتكلفة غير محدودة.
ميزانية وحدود العمال والتوكنات والوقت والدورات، circuit breaker.
Path Traversal / Symlink
كتابة ملف خارج المشروع عبر مسار أو رابط رمزي.
canonical path check، sandbox/allowlist، اختبار قبل الكتابة.
State Corruption
تكرار حدث أو انقطاع يسبب تنفيذ المهمة مرتين.
transactional event journal، idempotency key، leases ومصالحة.
Workspace Conflict
عاملان يغيران ملفًا مشتركًا ثم يفقد أحدهما تحديث الآخر.
Worktrees، نطاق ملفات، diff gate، merge conflict handling.
Approval Spoofing
محتوى من نموذج أو ملف يزعم أن المستخدم وافق.
الموافقة لا تأتي إلا من قناة UI موثوقة مع معرف إجراء وصلاحية زمنية.
Log Leakage
نسخ prompt حساس أو بيانات اعتماد في log أو artifact.
تقليل البيانات، redaction، صلاحيات قراءة، retention محدود.

يجب أن يغطي نموذج التهديد على الأقل المخاطر التي صنفها OWASP GenAI Top 10 2026: Prompt Injection، Sensitive Information Disclosure، Excessive Agency، Supply Chain، Data/Model Poisoning، Unbounded Consumption، Misinformation، Hidden Context Exposure، Vector/Embedding Weaknesses، Improper Output Handling. تُراجع المخاطر ذات الصلة عند كل إصدار أو إضافة MCP/أداة جديدة. [S9]
11.5 الخصوصية
•  يجب أن تكون معالجة المشروع محلية افتراضيًا، وأي إرسال إلى مزود نموذج يتم عبر إعدادات OpenCode/مزود المستخدم.
•  لا تُخزن مفاتيح المزود داخل ملفات TITAN أو قواعد بياناته أو التقارير.
•  يجب أن يتيح المستخدم حذف ذاكرة المشروع وسجل TITAN وفق سياسة retention دون العبث بسجل OpenCode خارج نطاق المنتج.
•  يجب أن تُحجب مسارات المستخدم والأسماء والبيانات الحساسة من تقارير المشاركة عند تفعيل وضع redacted export.

12.1 سياسة إعادة المحاولة
يجب أن ترتبط إعادة المحاولة بتصنيف الخطأ. أخطاء rate-limit والاتصال قد تعاد بعد backoff؛ أخطاء schema أو صلاحيات أو مسار غير آمن لا تعاد تلقائيًا؛ فشل اختبار يعاد بعد إصلاح له علاقة؛ وتعارض الدمج لا يعاد عبر إعادة تشغيل عامل عشوائي. الحد الافتراضي المقترح 3 محاولات لكل مهمة قابلة للإصلاح، مع حد إجمالي للـ Run.
12.2 التعافي بعد إعادة التشغيل
1. تحميل config وschemaVersion وقاعدة البيانات.
2. التحقق من سلامة سجل الأحداث والمعاملات الأخيرة.
3. قراءة المهام والعوامل والـ leases المعلقة.
4. مطابقة session IDs مع حالة OpenCode الحالية عبر واجهات V2 المتاحة.
5. وضع الأنشطة غير القابلة للحسم في NEEDS_RECONCILIATION بدل افتراض النجاح.
6. إعادة جدولة المهام الآمنة فقط؛ كل عملية غير idempotent تحتاج فحص أثرها أولًا.

13.3 معنى النجاح
تعريف النجاح — Run ناجح فقط عندما تتحقق كل معايير القبول الإلزامية، وتكون بوابات الاختبار والمراجعة المطلوبة PASS، ولا يوجد إجراء حساس غير معتمد، ويُحفظ التقرير النهائي. أي نقص يجب أن يظهر كـ BLOCKED أو WAIVED بموافقة، لا كنجاح كامل.

14.2 مجموعة المقارنة
يجب أن تُبنى مجموعة اختبار من 50–100 مهمة أولية، مع توسيعها تدريجيًا. تتوزع على إصلاح أخطاء، وميزات، وواجهات، وAPI، وقواعد بيانات، واختبارات، وأمان، وإعادة هيكلة، ومهام متعددة المكونات. تُستخدم مهام عامة ومهام من مستودع المشروع نفسه، مع تقسيم مجموعة تدريب/ضبط ومجموعة احتفاظ (holdout) لا تُستخدم لتحسين المطالبات.
14.3 خطوط الأساس
•  OpenCode V2 وحده مع نفس النموذج والطلب والميزانية.
•  OpenCode V2 مع تنسيق بسيط محدود (وكيل قائد وعامل واحد) لقياس عائد التعقيد.
•  TITAN في وضع عامل واحد.
•  TITAN في وضع التوازي المحدود.
•  اختياريًا مقارنة مع أدوات خارجية بعد التحقق من توافق إصدارها وترخيصها ونطاقها.

14.5 طريقة المقارنة المنصفة
•  تثبيت نسخة OpenCode والنموذج والميزانية والـ prompt والبيئة على كل خط أساس.
•  تنفيذ المهام العشوائية أو ترتيبها بالتناوب لتقليل تأثير تغير الخدمة والزمن.
•  تكرار المهمات المتأثرة بالعشوائية 3 مرات على الأقل وإظهار التشتت، لا أفضل نتيجة فقط.
•  تحكيم بشري أعمى لعينة من diff وتقارير المراجعة وفق rubrics معلنة.
•  نشر النتائج السلبية والتكلفة والوقت وعدد المحاولات؛ لا تُحذف حالات الفشل من الحساب.
ملاحظة بحثية — دراسة Microsoft Research المنشورة في أكتوبر 2026 على CRBugBench وجدت أن أفضل إعداد مدروس التقط 71.9% من العيوب ضمن أول خمسة تعليقات، مع تراجع الأداء في التغييرات المعقدة التي تتطلب استدلالًا غير محلي. لذلك لا ينبغي استخدام وكيل المراجعة كبديل وحيد للاختبارات الآلية أو المراجعة البشرية. [S10]

16. القيود والافتراضات والقرارات المفتوحة
16.1 القيود التقنية
•  OpenCode V2 يختلف عن V1 في واجهة الإضافات وواجهات الخادم والعملاء؛ إضافات V1 لا تعمل في V2 بمجرد نقل الملف أو تغيير اسم إعداد التسجيل. [S2]
•  واجهة V2 متغيرة نسبيًا؛ يجب تثبيت إصدار ⁦@opencode/plugin⁩ وإجراء contract tests عند كل ترقية.
•  تدفق أحداث OpenCode متطاير؛ لا يستخدم كسجل durable وحيد. [S5]
•  بعض خيارات إعداد وكيل قد تُحفظ دون أن تُرسل فعليًا مع طلب النموذج؛ لا يُبنى التوجيه على خاصية غير مفعلة في الإصدار المستهدف. [S4]
•  عمليات Worktree وإدارة الملفات تعتمد على Git والبيئة ونظام الملفات؛ يجب اختبارها على الأنظمة المدعومة.
•  استخدام عدة نماذج لا يضمن جودة أعلى؛ اختيار النموذج يقاس ويُراجع دوريًا.
16.2 الافتراضات
•  يملك المستخدم OpenCode V2، ويستطيع تهيئة مزود ونموذج مدعوم.
•  يوجد Git في معظم المشاريع المستهدفة؛ عند غيابه يعمل وضع محدود أحادي المساحة ويعطل التوازي الكتابي.
•  يُبنى المنتج أولًا محليًا وعلى مستخدم واحد؛ تعدد المستخدمين عن بعد خارج الإصدار الأول.
•  تُحدد سياسة الترخيص النهائية بعد مراجعة اعتماديات المنتج ومكونات OpenCode.
•  تبدأ أرقام الأداء الواردة كأهداف قياس، وتعدل بعد PoC على جهاز مرجعي معلن.

ملحق ب — نموذج تقرير التسليم
القسم
المحتوى المطلوب

Succeeded / Partial / Blocked / Failed مع سبب.
نطاق التغيير
ملخص الملفات والمكونات والسلوك.

كل معيار وما يثبت PASS أو سبب BLOCKED/WAIVED.

المراجعة

الأمن

الموارد
النماذج، الاستخدام المعلن، التكلفة التقديرية/الفعلية، وعدد المحاولات.
المخاطر المتبقية
أي اختبار لم يعمل، أو سلوك غير مؤكد، أو قرار ينتظر الإنسان.
الروابط
Run ID، Task IDs، Session IDs، Worktree/branch، artifacts.
ملحق ج — نقاط لا ينبغي أن تُبنى على افتراضات
•  لا تفترض أن أسماء الدوال في أمثلة قديمة (مثل ⁦session.create⁩ أو ⁦session.prompt⁩ أو ⁦ctx.tool.define⁩) هي نفسها في إصدار V2 المثبت؛ راجع types الفعلية ومرجع API في R0.
•  لا تفترض أن كل حدث OpenCode يصل مرة واحدة أو بترتيب مضمون؛ استخدم معرفات أحداث ومصالحة واستعادة.
•  لا تفترض أن Worktree يعزل ملفات خارج Git أو موارد نظام التشغيل أو خدمات الاختبار الخارجية؛ يجب تحديد حدود العزل.
•  لا تفترض أن السعر المحسوب يساوي الفاتورة؛ المزود قد يختلف في التسعير والخصومات والـ caching والرسوم.
•  لا تفترض أن مراجعة AI تلتقط كل العيوب؛ اربطها بالاختبارات والمراجعة البشرية للمخاطر العالية.
•  لا تفترض أن زيادة عدد الوكلاء ترفع الجودة؛ اختبر الفائدة الصافية مقابل التكلفة والتعارض والوقت، ولا تعتبر عدد الوكلاء أو الرموز دليلًا على جودة النتيجة.
